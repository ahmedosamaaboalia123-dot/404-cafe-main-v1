# مراجعة الفرونت وخطة التكامل مع الباك إند

> تاريخ المراجعة: 12 سبتمبر 2026  
> نطاق المراجعة: `new desktop` مقابل عقد الباك إند الحالي في `404-coffee-backend-v2` ووثائق `backend-design/final-2`  
> الهدف: تحديد الجاهز والناقص والمخالف، ووضع خطوات تنفيذ تجعل الباك إند هو مصدر الحقيقة لكل العمليات.

## 1. الحكم التنفيذي

الفرونت **جاهز بصرياً بدرجة جيدة** ويحتوي على أغلب الصفحات المطلوبة، كما أن بناء الإنتاج ينجح. لكنه **غير جاهز للتكامل الكامل حالياً**؛ لأن غالبية صفحات الإدارة ما زالت تستخدم عقد API قديم، وبعض تدفقات العميل والطاولة تستخدم `localStorage` كمصدر للطلبات، وتوجد وظائف جديدة للـAPI داخل المشروع لكنها غير موصلة بالشاشات الفعلية.

التصنيف العام:

- **جاهز بصرياً:** معظم صفحات الإدارة، العميل، والطاولة.
- **جاهز جزئياً للربط:** bootstrap، كتالوج المنتجات، realtime sync، وبوابات API الجديدة للعميل والطاولة.
- **يحتاج ترحيل عقد API:** الموردون، المواد الخام، التحذيرات، المشتريات، المرتجعات، المنتجات، الموظفون، الدرج، الطلبات، التحضير، المناديب، العملاء، والتقارير.
- **ناقص كشاشات مستقلة:** سجل الأحداث الشامل، إدارة التقييمات، مركز الإشعارات الكامل، وبعض إجراءات الحضور والأجهزة والتوصيل والطباعة.
- **مانع تكامل حرج:** المسارات القديمة تبدأ من `/api` بينما الباك الحالي يبدأ من `/api/v1`، مع اختلاف أسماء الحقول والـHTTP methods وشكل القوائم.

هذه المراجعة لا تعتبر نجاح `npm run build` دليلاً على صحة التكامل؛ البناء يثبت صحة التجميع فقط، ولا يثبت أن المسارات والـDTOs وحالات العمل متطابقة مع الباك.

## 2. نتيجة الفحص الفني

- `npm run build`: **ناجح**.
- لا يوجد `lint` أو `test` أو `typecheck` في `package.json`.
- يوجد تحذير حجم: الحزمة الرئيسية تقارب `596 kB` قبل الضغط، وملف Dashboard يقارب `374 kB`.
- يوجد lazy loading للصفحات، لكنه غير كافٍ لتقليل الحزمة الرئيسية إلى الحد الموصى به.
- المشروع RTL ومتجاوب في أجزاء كثيرة، وتوجد قواعد mobile واضحة، لكن يلزم اختبار فعلي لكل dialog/table على عرض 320px و375px و768px.

## 3. مشاكل مشتركة تمنع التكامل الصحيح

### 3.1 توحيد نسخة الـAPI

الإعداد الحالي يجعل `baseURL=/api`. القسم الجديد فقط داخل `endpoints.v1` يضيف `/v1`. بقية الخدمات تطلب مسارات مثل `/suppliers` و`/orders`، وبالتالي تصل إلى عقد قديم غير موجود في الباك الحالي.

المطلوب:

1. جعل `VITE_API_BASE_URL` يشير إلى `/api/v1`، أو الإبقاء على `/api` بشرط أن تبدأ **كل** endpoints بـ`/v1`.
2. منع الجمع بين الطريقتين في نفس المشروع.
3. حذف المسارات القديمة بعد ترحيل آخر شاشة حتى لا يحدث fallback صامت إلى سلوك غير صحيح.

### 3.2 شكل الاستجابة

الباك يعيد envelope موحداً:

```json
{
  "ok": true,
  "data": {},
  "meta": {}
}
```

الفرونت يستخدم حالياً أشكالاً متعددة: `response.data || response`، و`response?.data ?? response`، وأحياناً يفترض أن `data` array مباشرة. المطلوب إنشاء دالتين مركزيتين:

```js
unwrapData(response)       // تعيد response.data فقط بعد التحقق من ok
unwrapPage(response)       // تعيد { items, page, limit, total, pages, ... }
```

ويجب عدم تخمين شكل الاستجابة داخل كل component.

### 3.3 Pagination

الوثيقة والباك يحددان `limit=10` افتراضياً وبحد أقصى 10 للجداول التشغيلية. الفرونت يرسل `pageSize` بقيم 30 و50 و100 في عدة خدمات. المطلوب:

- استبدال `pageSize` بـ`limit`.
- الاحتفاظ بـ`page` و`limit` في URL query عند الحاجة.
- عرض `total` و`pages` من `meta` وعدم حسابهما من طول الصفحة الحالية.
- كل جدول في الموردين، المواد، السحوبات، المشتريات، المرتجعات، الموظفين، الأجهزة، الحضور، الطلبات، العملاء، المناديب، الدرج، التقييمات وسجل الأحداث يجب أن يستخدم pagination حقيقي من السيرفر.

### 3.4 Mongo IDs

يوجد تحويل صريح لـ`productId` و`productSizeId` و`addonIds` و`delegateId` إلى `Number`. هذا يكسر Mongo ObjectId. كل المعرفات يجب أن تبقى `String` من لحظة قراءة الكتالوج حتى إرسال الطلب ومقارنة أحداث realtime.

### 3.5 Idempotency وسباقات المستخدم

بعض البوابات ترسل `Idempotency-Key`، لكن كثيراً من عمليات المال والمخزون والطلبات لا ترسله. المطلوب wrapper موحد للعمليات الحساسة، مع الاحتفاظ بالمفتاح نفسه عند إعادة المحاولة لنفس الضغط، وتوليد مفتاح جديد للعملية الجديدة.

يجب أيضاً إرسال `expectedVersion` في تعديل الطلب وإلغائه وإضافة الأصناف وتحديث الحالات. عند `409 VERSION_CONFLICT` يعاد تحميل العنصر وتظهر رسالة واضحة للمستخدم بدلاً من تكرار العملية تلقائياً.

### 3.6 المهلة وتجربة المستخدم

الـAxios timeout الحالي `30000ms` مخالف لهدف الاستجابة من نصف ثانية إلى ثانية. لا ينبغي ضبطه على ثانية واحدة لأن عمليات الطباعة والتصدير قد تستغرق أطول، لكن المطلوب:

- إظهار skeleton فوراً.
- اعتبار `1000ms` حداً للأداء يتم قياسه، لا مهلة قطع عامة.
- مهلة قراءة عادية 8–10 ثوانٍ، ومهلة أطول للتصدير/رفع الصور فقط.
- إلغاء الطلب السابق عند تغيير البحث أو الفلتر باستخدام `AbortController`.
- debounce للبحث من 250 إلى 350ms.
- عدم إعادة جلب شاشة كاملة بعد كل mutation؛ تحديث cache من response ثم مزامنة الحد الأدنى.

### 3.7 Realtime

الأساس موجود في `realtime.js`، لكنه غير موحد على مستوى الشاشات. المطلوب:

1. Socket يحمل الأحداث فقط، والـREST هو مصدر الحقيقة.
2. حفظ آخر `sequence` لكل room.
3. بعد reconnect استدعاء `/realtime/sync?rooms=...&afterSequence=...`.
4. تطبيق الحدث مرة واحدة؛ تجاهل أي sequence أقدم أو مكرر.
5. عند وجود gap يعاد تحميل query المعنية.
6. فصل rooms الخاصة بالإدارة عن tracking token الخاص بالعميل وtable token الخاص بالطاولة.

### 3.8 الأخطاء والصلاحيات

`errorHandler` الحالي يعرض `message` فقط. المطلوب التعامل مع `code` و`details` و`fieldErrors` و`requestId`. كما يجب أن تعتمد حماية الصفحات والأزرار على permission keys الفعلية، وليس أسماء أدوار ثابتة فقط. إخفاء الزر تحسين للواجهة، بينما الباك يظل صاحب قرار السماح.

## 4. مراجعة الموديولات

## 4.1 المصادقة وتهيئة لوحة الإدارة — جاهز جزئياً / أولوية حرجة

### الجاهز

- FingerprintJS يعمل ويرسل بصمة واسم الجهاز وUser-Agent.
- تخزين access/refresh tokens واستعادة الجلسة موجودان.
- `bootstrapV1()` موجود ويستوعب الموظف والدور والصلاحيات والإشعارات والوردية.
- refresh single-flight موجود لمنع عدة refresh requests متزامنة.

### المشاكل والناقص

- login وrefresh وlogout تستخدم `/auth/...` من دون `/v1`.
- refresh interceptor نفسه يبني `/auth/refresh` يدوياً.
- `me` و`logout-all` و`attendance/check-out` مبنية على عقد قديم؛ الباك يعتمد bootstrap وتدفقات حضور مختلفة.
- قبول الجهاز المعلّق يحتاج قراءة status/body وفق عقد `202 DEVICE_APPROVAL_REQUIRED` بدقة.
- حماية الـsidebar تعتمد جزئياً على `role.name` وعلى `page_key` قديم، ولا تغطي action permissions.

### التنفيذ المطلوب

- ترحيل login/refresh/logout إلى `/api/v1/auth/*`.
- جعل `bootstrapV1` هو طلب البداية الوحيد بعد وجود token.
- بناء `can(permissionKey)` مركزي واستخدامه للroute والأزرار معاً.
- عند تغيير `permissionsVersion` أو 401: مسح الجلسة وإعادة تسجيل الدخول مرة واحدة من دون loop.

## 4.2 Dashboard — قريب من الجاهزية

### الجاهز

- الصفحة والبطاقات والرسومات موجودة.
- endpoint جديد `/dashboard-screen` معرف بالفعل في `endpoints.v1.dashboard`.

### المطلوب

- `dashboardService` ما زال يستدعي `/dashboard`؛ يوصل إلى `/v1/dashboard-screen`.
- استخدام payload الشاشة المجمّع لتجنب عدة requests.
- ربط الفلاتر الزمنية بعقد الباك، وعرض حالات loading/empty/error لكل widget.
- تقسيم chart code لتقليل chunk الكبير.

## 4.3 الموردون — الواجهة موجودة / التكامل يحتاج ترحيل كامل

### الجاهز

- إنشاء مورد، قائمة، صفحة شخصية، المواد المرتبطة، وأزرار الدين والمستحق والدفعات ظاهرة.
- الأنواع الأربعة للحركة ممثلة في الواجهة.

### المشاكل والناقص

- القائمة تطلب `/suppliers` مع `pageSize` بدلاً من `/suppliers-screen?page&limit&search`.
- التعديل يستخدم `PUT` بدلاً من `PATCH`.
- الحذف غير موجود في العقد؛ المطلوب تغيير الحالة عبر `/suppliers/:id/status`.
- الحساب يستخدم `/transactions` بينما العقد هو `/account-entries`.
- لا توجد واجهة عكس قيد عبر `/supplier-account-entries/:id/reverse`.
- يجب عرض سبب رفض دفعة أكبر من الرصيد وعدم قص المبلغ في الفرونت.

### القبول

- القائمة 10 عناصر وتظهر الإجماليات الصحيحة.
- إنشاء دين/مستحق لا يغير الدرج.
- دفع دين أو تحصيل مستحق يتطلب وردية مفتوحة ويسجل حركة الدرج.
- المورد غير النشط يمنع قيداً جديداً ويسمح بالتسوية حسب قواعد الباك.
- كل صف يعرض التاريخ ومنشئ الحركة وحالة العكس.

## 4.4 المواد الخام والدفعات والسحب — الواجهة موجودة / العقد غير مطابق

### الجاهز

- تسجيل المادة، المورد، وحدات القياس، التحويل بين الكبيرة والصغيرة، حدود التحذير، صفحة التفاصيل، الدفعات، أولوية السحب، وسجل المواد المسحوبة موجودة بصرياً.

### المشاكل والناقص

- تستخدم `/raw-materials` القديمة بدلاً من `/raw-materials-screen` وعقد التفاصيل الحالي.
- التعديل `PUT` والحذف `DELETE` غير متوافقين مع lifecycle في الباك.
- الواجهة تسمح بإنشاء/تعديل/حذف batch مباشرة، بينما التسجيل مسموح من المشتريات فقط.
- إعادة ترتيب الأولوية يجب أن ترسل القائمة كاملة مع version مناسب.
- `pageSize` يجب أن يصبح `limit`.
- تحديد المورد يجب أن يحدث لحظة إنشاء المادة، ثم يعرض القفل وسببه وتاريخه عند استعمالها.

### القبول

- لا يوجد زر إضافة دفعة من صفحة المادة.
- السحب النهائي يختار batch والكمية، يخصم مرة واحدة، ولا يعرض زر استرجاع.
- المنتهي الصلاحية يظهر بتحذير ولا يمنع البيع.
- كل كميات العرض مشتقة من الوحدة الصغيرة، مع عرض التحويل للوحدة الكبيرة من دون Float.

## 4.5 التحذيرات — واجهة جيدة / مصدر بيانات قديم

### الجاهز

- الأنواع: مخزون منخفض، نافد، قرب انتهاء، ومنتهي الصلاحية.
- بطاقات إحصائية وفلاتر وجدول وتحديث realtime موجودة.

### المطلوب

- استبدال `/warnings` بـ`/warnings-screen` واستخدام `/warnings/summary` عند عدم وجود summary داخل screen response.
- إضافة تحذير الوردية المفتوحة كل 12 ساعة وعرض عمر الوردية وآخر تحذير.
- إرسال search/type/date/page/limit إلى السيرفر؛ الفلترة المحلية وحدها لا تكفي مع pagination.
- ربط event names الفعلية أو invalidation عن طريق event-to-query map مركزي.

## 4.6 المشتريات — واجهة واسعة / تحتاج إعادة توصيل

### الجاهز

- إنشاء فاتورة متعددة الموردين، مواد قابلة للبحث، سعر وكمية وإجمالي، غير مدرجة ومدرجة، تسجيل مادة، تقسيم حسب المورد، وعرض/طباعة موجودة في التصميم.

### المشاكل والناقص

- الخدمات تعتمد نموذج purchases قديم: approve/preview/cancel/receive-item ومسارات لا توجد في العقد الجديد.
- العقد الحالي يتمحور حول `purchase-groups` و`purchase-items/:id/register` و`register-many` و`split-by-supplier`.
- خيارات الوحدات الحالية تتضمن افتراض `BUNDLE` مبني على `material.unit` ويجب استبداله بالتحويل الفعلي المخزن للمادة.
- الطباعة يجب أن تستخدم `/purchase-groups/:id/print-data` و`/supplier-purchase-invoices/:id/print-data`.
- يلزم expectedVersion عند تعديل فاتورة ما زالت قابلة للتعديل.

### القبول

- إنشاء المجموعة لا ينشئ دين مورد.
- تسجيل item ينشئ batch واحدة فقط حتى مع double click.
- اكتمال كل items ينقل الفاتورة إلى المدرجة من response السيرفر.
- التقسيم ينتج فواتير الموردين الصحيحة من دون تغيير المجموعة الأصلية مرتين.
- لا يمكن تعديل صنف مسجل بطريقة تكسر batch؛ تعرض الواجهة السبب والإجراء المتاح.

## 4.7 مرتجعات المشتريات — الواجهة موجودة / العقد مختلف

### المطلوب

- استبدال `/returns` بـ`/purchase-returns-screen` و`/purchase-returns`.
- اختيار المادة ثم batch المتاحة من context الذي يعيده الباك، لا من cache قديم.
- إرسال الكمية بالوحدة الصغيرة أو DTO التحويل المتفق عليه.
- استخدام `/purchase-returns/:id/print-data` للطباعة.
- لا تسمح الواجهة بمرتجع أكبر من remaining، ولا تعتبر فحص الفرونت بديلاً عن رد الباك.
- توضيح أثر المرتجع على المخزون والحسابات طبقاً للحالة النهائية من السيرفر.

## 4.8 المنتجات والوصفات والتكلفة — التصميم موجود / يحتاج إعادة بناء service layer

### الجاهز

- الأقسام، المنتج، الصورة، الأنواع، الأحجام، سعر البيع، المواد وكمياتها، الظهور في المنيو، والتكلفة والربح ممثلة في الصفحة.

### المشاكل والناقص

- الفرونت يرسل منتجاً مركباً عبر `/products/configuration` كـmultipart، بينما الباك يوفر عمليات منفصلة للcategory/product/type/size/recipe/media.
- الحذف الفعلي لا يناسب المنتجات المستخدمة؛ يجب تطبيق status/menu visibility وفق العقد.
- تكلفة المنتج يجب عرضها من محاكاة batches في الباك، لا من آخر سعر شراء ولا من حساب browser.
- الصورة يجب رفعها عن طريق media flow ثم حفظ media reference.
- يلزم التعامل مع partial save: المنتج قد يُنشأ قبل إضافة النوع أو الحجم؛ الواجهة تعرض draft واضحاً وتسمح بالإكمال.

### القبول

- لا يظهر منتج في المنيو إلا إذا كان فعالاً، مرئياً، وله حجم صالح وسعر ووصفة قابلة للاستهلاك.
- كل ingredient يحفظ بالوحدة الصغيرة.
- تغير batch prices يغير expected cost من السيرفر.
- التكلفة الفعلية لا تظهر قبل الطلب، وتؤخذ من order/invoice بعد الخصم الحقيقي.

## 4.9 طلبات الإدارة: أونلاين وتيك أواي والطاولات — الواجهات موجودة / مانع حرج في العقد

### الجاهز

- صفحات البيع، الكروت، المتابعة، الإضافة، التحضير، الجاهز، الطاولات 1–20، سجل الطلبات، تفاصيل الطلب والطباعة موجودة أو ممثلة.
- توجد مفاتيح idempotency في بعض عمليات الطلب.

### المشاكل والناقص

- كل مسارات `/orders` الحالية قديمة، بينما الباك يوفر screen endpoints وcase commands متخصصة.
- تحويل ObjectIds إلى Number يكسر إنشاء الطلب.
- حالات الواجهة لا تغطي بدقة حالات التوصيل، طلب الإلغاء، الإلغاء الجزئي، الدفع، والتسليم.
- بعض الصفحات تفتح routes من نوع `busy/:type/:id` مبنية على تصور قديم.
- `DeliveryModal` يستخدم `MOCK_CUSTOMERS`.
- الإضافة والإلغاء وتغير الحالة يجب أن يرسل `expectedVersion` ويعالج 409.
- الطباعة يجب أن تستخدم `/orders/:id/print-data`.

### التنفيذ المطلوب

- بناء `ordersApi` واحد حسب commands في عقد الباك: إنشاء، تفاصيل، إضافة أصناف، إلغاء صنف/طلب، تحديث تحضير، إنهاء، دفع، طباعة.
- استخدام `/order-history-screen` للسجل و`/preparation-screen` للتحضير و`/tables-board` للطاولات.
- إبقاء كل IDs strings.
- بعد تأكيد الطلب، الاعتماد على response في تحديث المخزون الظاهر؛ لا تخصم الواجهة محلياً.
- عند الإلغاء، لا تضف الكمية محلياً؛ اعرض نتيجة reversal القادمة من السيرفر.

## 4.10 التحضير — واجهة جيدة / تحتاج حالات كاملة

### الجاهز

- تبويب جاري التحضير وجاهز، تفاصيل الأصناف، زر تم التحضير، وإحصائيات الجاهزية موجودة.

### المطلوب

- الترحيل إلى `/preparation-screen` لتقليل عدد الطلبات.
- دعم PENDING/IN_PREPARATION/READY/CANCELLED بحسب القيم الفعلية في العقد.
- منع الضغط المزدوج، وإرسال version، وإعادة التحميل عند conflict.
- إذا أضيف منتج لطلب READY يرجع الطلب تلقائياً إلى الحالية من response/event.
- الاشتراك في rooms المناسبة وتطبيق REST catch-up.

## 4.11 المناديب والتوصيل — الصفحات الأساسية موجودة / الوظائف التشغيلية ناقصة

### الجاهز

- إنشاء مندوب، قائمة، صفحة تفاصيل وجدول الطلبات موجودة.

### المشاكل والناقص

- تستخدم `/delegates` القديمة بدلاً من `/delegates-screen` للتجميع.
- pagination غير موجود فعلياً والقائمة تطلب 30 عنصراً.
- مقارنة `delegateId === Number(id)` خاطئة مع ObjectId.
- ناقص تعديل بيانات/حالة المندوب.
- ناقصة إجراءات assign، handover، reassign، failed، returned، admin-confirm-delivery، settle-cash.
- ناقص زر WhatsApp الموثق وتسجيل `/whatsapp-share-opened`.
- تنسيق العملة يظهر `ر.س` بينما النظام يستخدم الجنيه المصري.

### القبول

- الطلب الأونلاين لا يعتبر مسلماً بمجرد assign.
- handover يفعّل زر استلام العميل.

## 4.12 العملاء — الصفحات موجودة / العقد قديم

### الجاهز

### المطلوب

- تفاصيل العميل تستخدم `/customers/:id?include=orders,reviews,...` حسب العقد، بدلاً من request منفصل لكل جدول متى أمكن.
- التعديل `PATCH`، وإزالة delete غير المدعوم.
- استبدال mock المستخدم في DeliveryModal ببحث حقيقي في العملاء.
- كل جدول طلبات يستخدم pagination، مع زر print من print-data.
- العميل الذي ينشأ من checkout يجب أن يظهر بعد event/invalidation من دون duplicate حسب normalized phone.

## 4.13 تجربة العميل الأونلاين والتيك أواي — بوابة v1 موجودة / الشاشات لا تستخدمها بالكامل

### الجاهز

- حفظ آخر اسم وهاتف وعنوان محلياً للملء التلقائي.
- بوابة v1 للإنشاء والتتبع والبحث والإضافة والإلغاء والاستلام موجودة.
- صفحة متابعة غنية: barcode، حالات، تقدم، حالة كل صنف، وفاتورة.
- AI endpoint الجديد مستخدم.

### المشاكل والناقص

- إنشاء الطلب وبعض القوائم ما زال يستخدم العقد القديم.
- صفحة “طلباتي” تستدعي `listMyOrdersByPhone` القديم، ثم تعتمد جزئياً على نسخ localStorage.
- `customerOrdersService` ما زال يعدل الطلبات محلياً؛ هذا يسبب اختلافاً حتمياً بين جهازين أو بعد تنظيف المتصفح.
- لا توجد دالة v1 ظاهرة لإرسال review من العميل رغم وجود endpoint معرف.
- tracking socket يحتاج استخدام read token الصحيح وREST catch-up.

### قاعدة التخزين المحلي النهائية

يسمح في `localStorage` بحفظ آخر بيانات العميل ورقم الطلب والباركود وread/action tokens اللازمة. لا يحفظ الطلب الكامل كمصدر حقيقة. عند فتح الصفحة، تستخدم القيم المحلية للوصول، ثم تحمل الحالة من السيرفر.

### القبول

- DELIVERY يتطلب الاسم والهاتف والعنوان؛ PICKUP يتطلب الاسم والهاتف فقط.
- نفس الهاتف يربط الطلب بسجل العميل وفق تطبيع الباك.
- إضافة صنف تستخدم رقم الطلب الحالي ولا تغير profile المخزن.
- زر الاستلام للأونلاين يتفعل بعد handover للمندوب؛ التيك أواي يتيح التقييم بعد إنهاء الإدارة.
- كل تحديث يظهر realtime ويمكن استعادته بعد انقطاع الاتصال.

## 4.14 تجربة الطاولة — التصميم موجود / دمج v1 غير مكتمل

### الجاهز

- الرئيسية والمنيو والفلتر والسلة والطلبات والتتبع والتقييم وخدمات الجرسون موجودة.
- flow الاقتراح الجديد موجود في `tableGateway`: bootstrap، submit proposal، current، cancel، service، review.
- العميل لا يؤكد طلب المطبخ مباشرة في عقد v1.

### المشاكل والناقص

- الشاشات ما زالت تستدعي وظائف session/order قديمة وتستخدم `tableOrdersService` وlocalStorage للطلبات.
- routes تحتوي redirect ثابتاً إلى طاولة رقم 4؛ هذا غير صالح للإنتاج.
- يوجد route وواجهة chatbot للطاولة رغم أن المواصفات طلبت إزالة الباريستا الذكي من قسم الطاولة.
- cart المحلي مقبول مؤقتاً قبل الإرسال، أما الطلب والمتابعة فمصدرهما السيرفر.
- يجب الحصول على table token من QR secret، لا من رقم الطاولة وحده.

### التنفيذ المطلوب

- إزالة redirects الثابتة `/table/4`، وفتح الطاولة من QR يحمل table number/secret.
- توصيل السلة بـ`submitV1TableProposal`، ثم انتظار مراجعة الإدارة.
- عرض REQUESTED/UNDER_REVIEW/CHANGES_REQUESTED/CONFIRMED/REJECTED/CANCELLED بوضوح.
- بعد التأكيد، تتبع order/session من endpoint المخصص وأحداث realtime.
- إزالة route ورابط chatbot للطاولة.

## 4.15 خدمات الطاولات — واجهات الطرفين موجودة / مسارات الإدارة قديمة

### الجاهز

- الأنواع المطلوبة ممثلة في تجربة الطاولة، وصفحة الإدارة فيها الحالية والمنتهية وزر التعامل.

### المطلوب

- طرف الطاولة يستخدم v1 services فقط مع table token وidempotency.
- طرف الإدارة يستخدم `/table-services-screen` و`/table-service-requests/:id/resolve` بدلاً من `/table-sessions/service-requests/...`.
- دعم الحالات OPEN/RESOLVED/CANCELLED كما في العقد.
- إظهار نوع الطلب والتفاصيل والطاولة والوقت والمدة والموظف الذي تعامل معه.
- realtime مع صوت/عداد اختياري وعدم إنشاء duplicate عند reconnect.

## 4.16 الدرج — واجهة أساسية موجودة / تكامل مالي يحتاج ترحيل

### الجاهز

- فتح وردية، رصيد افتتاحي، وارد/صادر يدوي، إغلاق، سجل ورديات وتفاصيل موجودة.
- توجد idempotency keys في الخدمة.

### المشاكل والناقص

- `/cash-drawer-screen` غير مستخدم، والصفحة تبني الحالة من عدة endpoints قديمة.
- history يرسل `pageSize:50`.
- ناقص transactions pagination، alerts، reverse transaction، وprint-data.
- نوعا `COLLECTION` و`EXPENSE` يحقنان في payload؛ يجب مطابقتهما بالـenum النهائي للباك.
- التحذير كل 12 ساعة يحتاج عرضاً واضحاً مع acknowledgement إن كان العقد يوفره.

### القبول

- الرصيد الافتتاحي يظهر في الرصيد ولا يدخل الإيرادات أو المصروفات.
- الإغلاق يعرض expected وcounted والفرق وعجز/زيادة.
- كل حركة آلية أو يدوية تحمل source/entity/date/employee.
- العكس ينشئ حركة مقابلة ولا يعدل السجل القديم.
- فاتورة كل وردية تأتي من `/print-data`.

## 4.17 الموظفون والأجهزة والحضور والصلاحيات — التصميم جزئي / يحتاج ترحيل كبير

### الجاهز

- إنشاء موظف، صفحة شخصية، عرض الاسم والمنصب والباسورد، الأجهزة، وصلاحيات الصفحات موجودة.
- backend يحمي password بإرجاعه فقط لمن لديه الصلاحية؛ الواجهة قادرة على إظهاره.

### المشاكل والناقص

- تستخدم `/users` بدلاً من `/employees-screen` و`/employees`.
- التعديل `PUT` بدلاً من `PATCH`.
- الأجهزة تقرأ بمسار موظف قديم، بينما قائمة pending الموحدة هي `/employee-devices`.
- approve/block paths القديمة مختلفة، ويوجد reject غير موجود كقرار نهائي مستقل في العقد الحالي.
- صلاحيات “الصفحات” القديمة ليست permission matrix الكاملة.
- ناقصة إدارة roles، الحضور paginated، تفاصيل سجل حضور، adjustment، force-close، والانصراف الإداري المرتبط بالوردية.
- `GET /employees/:id` يجب أن يطلب includes المطلوبة: password/devices/permissions/attendance/activity حسب صلاحية المشاهد.

### القبول

- جهاز جديد يعرض pending ولا يفتح النظام حتى الموافقة.
- أكثر من جهاز يمكن اعتماده، والبلوك يمنع الدخول فوراً حسب العقد.
- DENY يتغلب على ALLOW، وتغيير الصلاحية يبطل token القديم.
- login يسجل حضوراً واحداً مفتوحاً فقط.
- الانصراف الإداري يرفض إذا كان للموظف درج مفتوح ويعرض رابط الدرج.

## 4.19 سجل الأحداث الشامل — غير موجود كواجهة

يلزم إنشاء route وصفحة sidebar بصلاحية مستقلة. الصفحة تستخدم `/audit-events-screen` بفلترة actor/action/entity/date/requestId/page/limit، وتفتح `/audit-events/:id` للتفاصيل. Timeline لأي كيان يستخدم `/entities/:entityType/:entityId/timeline`. التصدير يستخدم job endpoints. يجب عرض before/after والسبب والجهاز وIP والوقت والrequestId من دون تنفيذ أي تعديل على الحدث.

## 4.20 التقييمات — موجودة عند العميل والطاولة / إدارة التقييمات ناقصة

يلزم صفحة إدارة للقائمة `/reviews` مع pagination وفلترة، تفاصيل الطلب، moderation، وإظهار حالة التقييم. تقييم العميل العام يحتاج توصيل endpoint v1، وتقييم الطاولة موجود في gateway لكنه يحتاج ربط الشاشة. يمنع إنشاء أكثر من تقييم لنفس الطلب حسب رد الباك، وتعرض الواجهة التقييم السابق بدلاً من تكراره.

## 4.21 الإشعارات — بيانات bootstrap موجودة / مركز الاستخدام ناقص

الـstore يحتفظ بالإشعارات، لكن لا توجد دورة مكتملة للعرض/القراءة/العداد والمزامنة. يلزم ربط notification endpoints الفعلية، تحديث badge عبر realtime، وعدم إعادة جلب bootstrap كاملاً لكل إشعار. تحذير الوردية وخدمات الطاولة والطلبات الجديدة أهم مصادر الإشعارات.

## 4.22 الصور والوسائط — العرض موجود / إدارة الرفع غير مكتملة

صور المنتجات تعرض، لكن product service القديم يرفع multipart مباشرة. المطلوب استخدام media endpoints الحالية، التحقق من النوع والحجم، عرض progress، ثم تمرير media id عند حفظ المنتج. صورة fallback خارجية ينبغي استبدالها بأصل محلي أو URL من الباك لتجنب اختلاف العرض وانقطاع المصدر.

## 6. بنية Frontend مقترحة للتكامل

```text
src/
  api/
    client.js                 # auth, refresh, timeout, envelope, request-id
    errors.js                 # تحويل أكواد الباك إلى أخطاء واجهة
    idempotency.js            # مفتاح ثابت لكل mutation attempt
    query.js                  # page/limit/search/date serializers
  realtime/
    socket.js                 # اتصال واحد لكل نوع مستخدم
    sync.js                   # sequence + REST catch-up
    eventQueryMap.js          # أي حدث يحدث أي React Query cache
  modules/<module>/
    api/<module>.api.js       # المسارات وDTOs فقط
    adapters/<module>.js      # backend DTO -> UI model
    hooks/<module>.queries.js # React Query queries/mutations
    pages/
    components/
    validation/
```

القواعد:

- component لا يستدعي `apiClient` مباشرة.
- لا توجد endpoints نصية داخل pages.
- adapter واحد فقط يحول DTO؛ لا تتكرر أسماء status وترجمة العملة في كل صفحة.
- كل mutation حساسة ترسل idempotency وexpectedVersion عندما يطلبهما العقد.
- React Query هو cache، والباك هو مصدر الحقيقة.

## 7. ترتيب التنفيذ المقترح

### المرحلة 1 — طبقة التكامل المشتركة

1. توحيد `/api/v1`.
2. توحيد envelope/errors/pagination.

### المرحلة 2 — البيانات المرجعية والمخزون

الموردون ثم المواد الخام ثم التحذيرات ثم المشتريات ثم المرتجعات ثم المنتجات والوسائط. هذا الترتيب يحافظ على اعتماد كل موديول على السابق.

معيار الإتمام: رحلة إنشاء مورد → مادة → فاتورة شراء → تسجيل batch → ظهور تحذير/تكلفة منتج تعمل من الواجهة إلى MongoDB وتعود للواجهة.

### المرحلة 3 — الموظفون والدرج

الموظفون، الأجهزة، الأدوار والصلاحيات، الحضور، الدرج وتنبيه 12 ساعة.

معيار الإتمام: جهاز جديد ينتظر الاعتماد، الموظف يدخل ويسجل حضوراً، يفتح درجاً، يسجل حركة، يغلقه، ثم ينصرف.

### المرحلة 4 — طلبات الإدارة والتحضير والطاولات

ترحيل catalog POS، إنشاء الطلب، إدارة الأصناف، الإلغاء، preparation screen، tables board، proposals، services، الدفع والطباعة.

معيار الإتمام: الطلب يخصم المخزون مرة واحدة، الإلغاء يعكسه مرة واحدة، وسباق ضغطين ينتج عملية واحدة أو 409 مفهوم.

### المرحلة 5 — العميل والمناديب والتقييم

إنشاء العميل تلقائياً، checkout، التتبع، إضافة صنف، طلب إلغاء، assign/handover/deliver/settle، الاستلام، التقييم، وWhatsApp.

معيار الإتمام: رحلة DELIVERY كاملة ورحلة PICKUP كاملة تعملان بعد refresh ومن جهاز آخر من دون الاعتماد على نسخة order محلية.

### المرحلة 6 — التقارير والسجل والإشعارات

التقارير المجمعة والتفصيلية والتصدير، audit UI، reviews moderation، notification center.

معيار الإتمام: الأرقام تتطابق مع الفواتير والدرج والمخزون، وكل command سابق يظهر في audit timeline.

### المرحلة 7 — الجودة والأداء

- contract tests لكل API adapter.
- integration tests للرحلات الحرجة.
- Playwright لرحلات admin/customer/table.
- اختبار 320/375/768/1024/1440px وRTL ولوحة المفاتيح.
- قياس p95 للطلبات السريعة بهدف 500–1000ms.

## 8. مصفوفة اختبارات القبول الإلزامية

يجب قبل اعتبار التكامل مكتملاً اجتياز الحالات التالية:

1. double click وretry بنفس idempotency key لا ينشئان سجلين.
2. مستخدمان يعدلان نفس order/material؛ الثاني يستقبل 409 ويعيد التحميل.
3. socket ينقطع ثم يعود؛ لا تفقد أحداث ولا تتكرر.
4. انتهاء access token أثناء عدة requests يؤدي إلى refresh واحد.
5. تغيير الصلاحيات أثناء الجلسة يمنع العملية التالية ويعيد bootstrap/login حسب العقد.
6. كل قائمة تتعامل مع أول/آخر/صفحة فارغة وبحث وتغيير filter.
7. القيم المالية والكميات تعرض Decimal strings بدقة من دون أخطاء Float.
8. إلغاء طلب كامل وجزئي يعيد المخزون طبقاً لسجلات الباك.
9. batch منتهية تبقى قابلة للاستهلاك وتظهر في التحذيرات.
10. دفعة مورد أكبر من الرصيد ترفض برسالة مفهومة.
11. الرصيد الافتتاحي لا يدخل التقارير، والعجز/الزيادة يظهران عند الإغلاق.
12. وردية مفتوحة تستقبل تحذيراً عند كل مضاعف 12 ساعة من دون duplicate.
13. proposal الطاولة لا يصبح order قبل تأكيد الإدارة.
14. إضافة صنف لطلب READY تعيده للتحضير.
15. DELIVERY لا يتيح استلام العميل قبل handover، وPICKUP يتيح التقييم بعد الإنهاء.
16. الطباعة تستخدم snapshot من print-data ولا تجمع الفاتورة من state الشاشة.
17. refresh للمتصفح أو فتح جهاز ثانٍ يعرض نفس حالة الطلب.
18. كل عملية تظهر بالتاريخ والموظف والكيان والrequestId في سجل الأحداث.

## 9. تعريف “جاهز 100%” للفرونت

لا يعتبر الفرونت جاهزاً بالكامل إلا عند تحقق الآتي معاً:

- لا يوجد استدعاء لمسار قديم أو endpoint مكتوب مباشرة داخل page.
- لا توجد بيانات `MOCK_*` في أي تدفق إنتاجي.
- لا يوجد order أو inventory أو money state يعتمد على localStorage كمصدر حقيقة.
- جميع الجداول server paginated بحد 10.
- كل DTO يطابق validation schemas في الباك، وكل ID يبقى string.
- كل command حساس يدعم idempotency/version conflict.
- realtime يدعم sequence وREST catch-up.
- اختبارات العقد والتكامل وE2E ناجحة.
- رحلة المورد والمخزون والمشتريات والمنتجات والطلب والطاولة والعميل والمندوب والدرج والموظف والتقارير والسجل تعمل كاملة.
